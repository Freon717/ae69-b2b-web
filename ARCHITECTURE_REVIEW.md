# Архитектурный обзор — ae69-b2b-web

Дата: 2026-09-19. Ревизия: `c1fbb77` (v10).

## 1. Что это за репозиторий

Статический одностраничник для быстрой проверки B2B-каталога с телефона
(iPhone/APK-WebView) через GitHub Pages. Не production-витрина и не
справочник сотрудника — это отдельные репозитории (`ae69-b2b-app` — полный
B2B на TanStack Start, `ae69-catalog-web` — справочник сотрудника). Здесь
принципиально нет оптовых цен и нет сервера — только фронтенд + один JSON.

Состав репозитория:

| Файл | Роль |
|---|---|
| `index.html` | Разметка-каркас: шапка, поиск, вкладки, `<main id="app">` |
| `app.js` (745 строк) | Весь SPA: роутинг, индексация каталога, рендер, корзина, избранное |
| `styles.css` | Мобильные стили, без препроцессора |
| `catalog-public.json` (1.0 МБ, 2553 SKU / 1249 семейств / 11 категорий) | Единственный источник данных, коммитится как готовый артефакт |
| `manifest.webmanifest` | PWA (установка на домашний экран) |
| `.github/workflows/pages.yml` | Деплой на GitHub Pages при пуше в `main` |

Зависимостей нет: ни `package.json`, ни сборщика, ни линтера, ни тестов.

## 2. Архитектура

Классический "vanilla SPA" в одном IIFE:

- **Роутинг** — через `location.hash`, вручную (`parseHash`/`go`), с
  `history.pushState` и обработкой `popstate`/`hashchange`. Состояние вида —
  единственный объект `view`.
- **Данные** — `catalog-public.json` загружается один раз при старте
  (`fetch(...).then(indexData)`), индексируется в глобальные `Map`-подобные
  объекты (`famById`, `skuById`, `skusByFam`, `catById`). Дальше всё работает
  из памяти, без повторных сетевых запросов.
- **Рендер** — строковая конкатенация HTML (`homeHtml()`, `catalogHtml()`,
  `familyHtml()`, ...) → `el.innerHTML = ...`. Экранирование — вручную через
  `esc()` на каждой подстановке значения.
- **Состояние UI** — глобальные мутable-переменные (`selected`, `cart`,
  `favs`) на уровне замыкания модуля, без какого-либо стора/событийной шины.
  `cart`/`favs` персистятся в `localStorage`.
- **Обработка событий** — один делегирующий `el.onclick` в `bind()`,
  диспетчеризация по CSS-классам (`js-facet`, `js-fav`, `js-add`, `js-minus`/
  `js-plus`).
- **Отказоустойчивость** — `render()` оборачивает построение HTML в
  `try/catch` и выводит текст ошибки прямо в `#app`; плюс глобальный
  `window.onerror` в `index.html`. Простое, но рабочее решение для
  "не показывать белый экран" (это и есть история одного из прошлых фиксов,
  судя по `git log`: "Fix iPhone blank page").

Для объёма задачи (витрина на 745 строк без бэкенда) это адекватный и
осознанно простой выбор: ноль сборки, ноль установки зависимостей, можно
редактировать и деплоить прямо из GitHub UI.

## 3. Проверенные находки

### 3.1 Реальный баг: `resolveUnique()` тихо выбирает произвольный SKU при неоднозначности

```js
function resolveUnique(items, sel) {
  var matched = [];
  ... // фильтр по selected
  if (matched.length === 1) return matched[0];
  if (matched.length > 1) return matched[0];   // <-- тихо берёт первый
  return null;
}
```

Идея селекторов (`fam.sels`) — довести пользователя кликами по фасетам ровно
до одного SKU. Я прогнал полный `catalog-public.json` и проверил, для скольких
семейств полный набор фасетов **не** даёт единственный SKU:

- **50 семейств** — после выбора значений по всем `sels` всё ещё остаётся
  несколько SKU с одинаковой комбинацией атрибутов (например
  `hermetic-1.5` — 4 SKU на одну комбинацию, `fuse-норма` — 7 SKU без единого
  различающего атрибута).
- **1 семейство** (`batt-term`, «Клеммы аккумуляторные», 15 SKU) — у семейства
  вообще нет `sels`, поэтому карточка товара молча показывает `items[0]` — один
  случайный SKU из пятнадцати.

Практическое следствие: в этих ~51 семействах пользователь на телефоне видит
конкретный «Код АЭ» и артикул так, будто это однозначный результат его выбора
фасетов, а на самом деле под тем же выбором скрыто ещё N SKU с другим кодом
(возможно, другим цветом провода/длиной/фасовкой, не вынесенным в атрибуты).
Это не крэш и не то, что поймает `try/catch`, — это тихо неверные данные на
экране, самый неприятный тип бага.

**Исправлено**: при `matched.length > 1` `resolveUnique()` теперь возвращает
`null` (как при `matched.length === 0`), и показывается существующий текст
«Выберите параметры — появится конкретный SKU» вместо произвольного первого
совпадения. Регрессионный тест — `lib.test.js` → `resolveUnique` → «returns
null (not an arbitrary pick) when the facets don't disambiguate».

Получил доступ к `ae69-b2b-backend` (реальный источник, см. 3.2) и частично
закрыл первопричину: `side_of()` в его `scripts/import-price.py` узнавал
только слова «гнездо»/«штырь» в названии, а часть позиций (герметичные
колодки 1,5 мм, разъёмы прицепа, клеммы «под болт») пишут сторону прямо
словами «вилка»/«розетка» — 34 SKU из 7 подкатегорий вообще не получали
`attrs.side`. Починил (`ae69-b2b-backend@claude/fix-connector-side-detection`,
не смёржено — ждёт решения владельца репозитория), проверил на всём
`catalog.json` нулевую регрессию (ни одно уже выставленное значение не
изменилось), прогнал тесты каталога (44+5, зелёные). После пересборки
`catalog-public.json` семейство `hermetic-1.5` действительно обзавелось
фасетом «Сторона», которого раньше не было вовсе.

Это **не закрывает всю 51-семейственную неоднозначность**: у `hermetic-1.5`
после фикса `side` пара 8959/6890 (обе «вилка») всё ещё делит одну и ту же
комбинацию `section/kit/side`, потому что это физически разные корпуса
(СЦ7.501.607-01В и СЦАЗ-2-6), а такого атрибута («корпус»/«серия») в модели
данных просто нет. Проверил: список всех 51 неоднозначных `familyId`
до и после фикса — **идентичен**, фикс сократил степень неоднозначности
(4 SKU → 2 SKU на комбинацию у `hermetic-1.5`), но не убрал ни одного
семейства из списка целиком. Ввести недостающий атрибут — решение по
модели данных, а не однострочный фикс; оставил как есть, а не гадаю.

### 3.2 `catalog-public.json` — не воспроизводимый артефакт, но источник теперь известен

Файл на 1 МБ коммитится напрямую, без какого-либо генерирующего скрипта в
этом репозитории. Получив доступ к `ae69-b2b-app` и `ae69-b2b-backend`,
нашёл реальный источник — **`ae69-b2b-backend`**, не `ae69-b2b-app`, как я
ошибочно предполагал раньше по одному только названию (README самого
`ae69-b2b-web` тоже указывает на `ae69-b2b-backend` как на держателя
оптовых цен, а не на `ae69-b2b-app`). Конвейер:

```
ae69-b2b-backend/scripts/import-price.py   — .xls прайс → src/data/catalog.json
ae69-b2b-backend/src/lib/catalog/apply-rules.ts (applyCatalogRules) — группирует
  SKU в семейства, строит sels/values из фактических attrs
ae69-b2b-backend/scripts/export-public-catalog.mjs — пишет urlsized JSON
  (ровно тот формат, что использует app.js: n/t/c/s/sels/attrs/...)
```

Это не гипотеза — прогнал весь конвейер локально (`python3
scripts/import-price.py`, затем `node --experimental-strip-types
scripts/export-public-catalog.mjs`) и получил файл с тем же
`skuCount`/`familyCount`/`sourceDate`/`v`, что и текущий
`ae69-b2b-web/catalog-public.json`.

Риски (актуальность подтверждена, не снята):
- Нет способа проверить/воспроизвести файл в CI **этого** репозитория —
  экспорт живёт в `ae69-b2b-backend`, туда же нужен доступ.
- Формат (`n`, `t`, `c`, `s`, `sels`, `attrs`, ...) нигде не задокументирован
  здесь — вся схема восстанавливается чтением `app.js`.
- Дрейф между `ae69-b2b-web` и `ae69-b2b-backend` не виден, пока кто-то не
  сравнит вручную — именно так был найден фикс из 3.1 (отдельный от
  `resolveUnique`): `side_of()` в `import-price.py` пропускал 34 SKU, чьё
  название пишет сторону словом «вилка»/«розетка», а не «гнездо»/«штырь».

Рекомендация не изменилась: минимум — одна строка в README с указанием
конвейера выше. Максимум — GitHub Action в `ae69-b2b-backend`, который сам
пушит обновлённый `catalog-public.json` в `ae69-b2b-web` при изменении
прайса, вместо ручного копирования.

### 3.3 Ручной cache-busting в трёх местах — обновлён, не устранён структурно

`?vN` по-прежнему прописан вручную и раздельно в `index.html` (`styles.css`,
`app.js`) и в `app.js` (`lib.js`, `catalog-public.json`) — четыре места, не
три (добавился `lib.js` при выносе кода в 3.5). Статический `import` в
верху `app.js` не даёт вычислить версию динамически, как это сделано для
`BASE`/`CATALOG_URL`, поэтому единого источника правды как не было, так и
нет. Сейчас все четыре литерала подняты синхронно до `?v=11` (это было
нужно и само по себе: 3.1/3.5/3.6 меняли содержимое `app.js`/`lib.js` под
тем же `?v=10`, то есть уже выкаченный на прод код рисковал остаться в
кэше телефонов). Итог: баг с рассинхроном по-прежнему возможен при
невнимательности — просто в этот раз синхронизировано руками.

### 3.4 Экранирование сделано вручную, но последовательно

Проверил все точки `innerHTML =`: значения из данных везде проходят через
`esc()` перед вставкой (`row()`, `crumbs()`, атрибуты `data-*` в кнопках и
т.д.). Явных XSS-дыр не нашёл. Риск чисто процессный: в будущем легко забыть
`esc()` при добавлении нового поля — тесты или шаблонизатор с автоэкранированием
этого не ловят, полагаться приходится на code review.

### 3.5 Отсутствие тестов на чистые функции — исправлено

`parseHash`, `resolveUnique`, `availableOptions`, `orderOpts`, `packCopy`,
`stepOf`, `expandQ`, `esc`, `norm`, `compact`, `coverOf`, `attrToken` — все
эти чистые функции без DOM-зависимостей вынесены из `app.js` в отдельный
ES-модуль `lib.js` (без сборщика — обычный `<script type="module">`,
`app.js` импортирует их обратно) и накрыты `lib.test.js` (18 тестов,
`node --test lib.test.js`), по образцу `choice-grid.test.ts` в
`ae69-b2b-app`. Раньше единственной проверкой было ручное открытие на
телефоне по чек-листу из README — а баг из 3.1 такой чек-лист в принципе не
ловит, потому что он не про крэш, а про «показан не тот SKU»; теперь на этот
конкретный сценарий есть регрессионный тест.

### 3.6 Доступность — исправлено частично

Кнопка избранного (`.heart.js-fav`) теперь выставляет `aria-pressed`
("true"/"false") синхронно со своим текстом. Остальная доступность в
порядке: 44px тач-таргеты выдержаны почти везде, `aria-label` на иконочных
кнопках шапки есть.

### 3.7 PWA-иконок не было вовсе — исправлено

`manifest.webmanifest` не объявлял `icons` — «На экран Домой» на Android
дало бы дженерик-иконку. Хуже того, для iOS Safari манифест вообще не
используется для этой кнопки — нужен `<link rel="apple-touch-icon">` в
`<head>`, которого не было тоже, при том что README прямо продаёт установку
на iPhone. Добавлены `icon-192.png`/`icon-512.png` (сгенерированы из того
же брендового «AE 69» на `#1f4e79`, что и в шапке сайта), подключены в
`manifest.webmanifest` и как `apple-touch-icon`/`icon` в `index.html` —
заодно закрыло и старый 404 на `favicon.ico`.

### 3.8 Тесты не запускались автоматически — исправлено

`.github/workflows/pages.yml` только деплоит, ничего не проверяя. Добавлен
`.github/workflows/ci.yml`: `node --check` на `app.js`/`lib.js` +
`node --test lib.test.js` на каждый push в `main` и на каждый PR — теперь
регрессию вроде багa 3.1 CI поймает сам, а не только при ручном запуске.
